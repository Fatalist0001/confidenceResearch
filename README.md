## 1. Что это за проект

Когда языковая модель отвечает на вопрос, внутри неё считаются числа — так называемые
*скрытые состояния*. Идея проекта: снять эти числа в двух местах (перед первым токеном
ответа и после последнего токена ответа), а затем по ним обучить очень простую модель,
которая оценивает, насколько вероятно, что ответ модели **правильный**.

Зачем это нужно: LLM часто отвечает уверенно и при этом неверно. Если есть дешёвая
внутренняя оценка «можно ли доверять этому ответу», её можно использовать, чтобы
отбрасывать сомнительные ответы и отправлять их на повторную проверку, не переспрашивая
модель второй раз.

Что уже сделано: инструмент для снятия скрытых состояний, датасет из 6000 вопросов,
автоматическая разметка правильности ответов и её проверка человеком, baseline по
logprob/энтропии и проба на скрытых состояниях — для Qwen3.5-0.8B и Gemma 4 E2B.
Чего ещё нет: анализа (reliability diagram, разбор ошибок) и прогонов на других размерах.

## 2. Ключевые определения

**Скрытое состояние** — вектор чисел, который модель держит «в голове» на выходе
какого-то слоя в конкретной позиции текста. По сути это «мысли модели» в этот момент.
Пример: для Gemma вектор одного слоя в одной позиции — это 1536 чисел.

**Слой** — один из последовательных блоков модели, через которые проходит текст.
Чем слой дальше, тем «более абстрактная» информация. Пример: у Gemma 35 слоёв
(`report.md`, шапка), у Qwen — 24 слоя (`out/main_qwen08/config.json`, поле `n_layers`).

**Точка A** — последний токен промпта (части с вопросом) уже после того, как чат-шаблон
модели его отрисовал вместе с началом реплики ассистента. Это состояние, из которого
модель выдаёт **первый** токен ответа. Пример из данных: в первой строке основного
прогона промпт занимает позиции 0–48, значит A = позиция 48 (`meta.jsonl`, строка с
`id=sfq_21874`: `n_tokens=51`, `pos_a=48`).

**Точка C** — последний **содержательный** токен ответа, без служебных токенов конца
реплики. В том же примере `pos_c=50`, то есть ответ занял 2 токена
(`n_answer_tokens = pos_c - pos_a = 2`, `meta.jsonl`).

**Метка правильности (correct)** — 1 или 0: считается ли ответ модели верным по
отношению к эталонному ответу. 1 — верный, 0 — неверный, пусто — метка не проставлена
(строка не подходит для разметки). Подробно — в разделе 3.4.

**Проба (логистическая регрессия)** — разведочный эксперимент: берём простейшую линейную
модель, которая на вход получает скрытые состояние (один слой, одна точка), а на выход
выдаёт число от 0 до 1 — предполагаемую вероятность того, что ответ правильный, и
сравниваем её с метками. Это делается, чтобы понять, есть ли в скрытых состояниях
сигнал вообще. Проба сделана: у Qwen3.5-0.8B test AUROC 0.857, у Gemma 4 E2B — 0.935
(раздел 3.8 и 3.9).

**Baseline (logprob)** — грубая оценка для сравнения с пробой: логарифм того, какую
вероятность модель сама дала первому токену своего ответа. Чем выше число, тем
увереннее модель начала отвечать. Уже лежит в данных: `logprobs` в `meta.jsonl`.
Пример: в первой строке `logprobs = [-1.3574457168579102, -0.1390269696712494]`, то
есть первый токен ответа модель выдала с log p = −1.3574457168579102
(`meta.jsonl`, строка `id=sfq_21874`).

**AUROC** — метрика качества любой оценки «правильный/неправильный». Берётся одна
случайно взятая правильная и одна случайно взятая неправильная строка и смотрится,
чаще ли правильная получила более высокую оценку. 0.5 — «как угадывание», 1.0 —
«идеально». Значения в проекте есть: baseline 0.705–0.767 и проба 0.857–0.935 на
тесте (разделы 3.7–3.9).

## 3. Что сделано, по этапам

### 3.1 Инструмент `llama-hidden-states` (на базе llama.cpp)

**Что делает.** Загружает модель в формате GGUF, прогоняет через неё вопросы и для
каждого примера записывает скрытые состояния **всех слоёв** в двух точках — A и C.

**Что такое GGUF и llama.cpp** (кратко): GGUF — формат файла с весами модели;
llama.cpp — популярная библиотека-движок, которая запускает такие модели. Инструмент
написан поверх её публичного интерфейса и лежит в каталоге `llama.cpp-hiddenstates\`
(полная копия llama.cpp коммита `d4cff114c` с одним нашим примером) (`AGENTS.md`).

**Как устроен.** Вместо того чтобы вычислять вручную промежуточные величины,
используется встроенный механизм llama.cpp — колбэк `cb_eval` (функция, которую движок
вызывает по мере вычисления графа модели). В момент вызова мы:

1. в фазе «спросить» (`ask=true`) отвечаем «да, вычислять» только для тензоров
   (массивов чисел) с именем вида `l_out-N` — это выход слоя N. Остальное считать
   не нужно, это сильно ускоряет проход (`report.md`, §2.3);
2. в фазе вычисления читаем ровно одну строку такого тензора — ту, что соответствует
   позиции A или C. Тензоры `l_out-0 … l_out-34` существуют для всех 35 слоёв Gemma,
   а `l_out-0 … l_out-23` — для всех 24 слоёв Qwen (`report.md`, §4 и §8.1);
3. после прохода проверяем, что захвачен **каждый** нужный слой; если какой-то слой
   пропущен, строка помечается как пропущенная, а не портит данные
   (`report.md`, §8.2, п.1).

**Режимы.**

| Режим | Как включается | Что делает |
|---|---|---|
| одиночный (v1) | `-p "вопрос"` + `--answer "ответ"` | один пример, массивы формы `[L, D]`; **не изменялся** (`report.md`, §5) |
| пакетный (v2) | `--batch input.jsonl` | массовый прогон, массивы формы `[N, L_sel, D]`; добавлен рядом со старым (`report.md`, §6) |

**Флаги пакетного режима** (`report.md`, §6):

| Флаг | Значение |
|---|---|
| `--generate` | если у примера нет готового ответа — сгенерировать его жадно (argmax, температура 0) |
| `--max-new-tokens N` | бюджет сгенерированных токенов (в основном прогоне — 64) |
| `--max-len N` | предел длины примера; `n_batch = n_ubatch = --max-len`, по умолчанию 1024 |
| `--no-template` | не применять чат-шаблон, брать текст как есть |
| `--no-thinking` / `--thinking` | выключить/включить режим «размышления» в шаблоне; по умолчанию `--no-thinking`, значение пишется в `config.json` (`thinking`) |
| `--layers all\|4,8,12\|step=2` | сохранять не все слои, а выбранное подмножество |
| `--out <dir>` | куда писать результат |
| `--dump-tensors` | печатать имена всех тензоров графа (отладка) |

**Что сохраняется** (`report.md`, §6.4):

| Файл | Содержимое |
|---|---|
| `hidden_a.npy` | скрытые состояния точки A, float16, форма `[N, L_sel, D]` |
| `hidden_c.npy` | то же для точки C |
| `meta.jsonl` | по строке на пример: `id`, `row`, `n_tokens`, `pos_a`, `pos_c`, `answer`, `generated`, `truncated`, `status` (+ `reason` для пропущенных); **плюс все дополнительные поля входа** (`gold`, `gold_main`, `dataset`, `split`, `group`) копируются без изменений; **плюс `logprobs` и `entropies`** — статистика по каждому сгенерированному токену |
| `config.json` | модель, слои, `max_len`, `max_new_tokens`, `generate`, `template`, `thinking`, определения точек A и C, версия движка |

- `logprobs` — логарифм вероятности, которую модель дала выбранному токену;
  `entropies` — мера «неопределённости» распределения (энтропия). Считаются обычным
  softmax по сырым логитам, float32 (`report.md`, §8.2, п.4). Записываются **только**
  для строк, где был `--generate`; для строк с готовым ответом стоят `null`.
- Длина этих списков равна числу сгенерированных токенов (`report.md`, §8.3). В
  основном прогоне заполнены у всех 6000 строк, всего 39752 токена; диапазоны:
  `logprobs` от −4.745199680328369 до −7.812728597400564e-08, `entropies` от
  1.5455934772035107e-06 до 8.707919120788574 (`meta.jsonl`).
- `truncated=true` — генерация упёрлась в бюджет токенов, ответ обрезан. Такие строки
  **не пропускаются**, но получают пустую метку (см. 3.4).
- Возобновление: при повторном запуске уже обработанные `id` пропускаются, flush на
  диск каждые 16 примеров (`report.md`, §6.4).

**Значения `config.json` основного прогона:** модель `Qwen3.5-0.8B-BF16.gguf`,
`n_layers=24`, `n_embd=1024`, `layers` = 0…23, `n_layers_selected=24`, `max_len=1024`,
`max_new_tokens=64`, `generate=true`, `template=true`, `thinking=false`,
`batch=data\main.jsonl`, `n_examples=6000`, `llama_cpp_build=2`,
`llama_cpp_commit=c9b758d`, `ggml_version=0.15.3`, `version=1`
(`out/main_qwen08/config.json`).

**Проверки корректности и результаты** (все — `report.md`, указанные разделы):

| Проверка | Результат |
|---|---|
| Детерминизм: два одинаковых запуска | `.npy` байт-в-байт совпадают (одинаковый SHA-256) (§4, §7) |
| Инвариантность A: запись с `answer` и без | векторы A **байт-в-байт идентичны**; в прогоне без ответа A == C (§4, §7) |
| Пакетный режим против одиночного | `hidden_a`/`hidden_c` **байт-в-байт** совпадают с векторами `[L, D]` из v1 (§7) |
| Независимость от порядка примеров (20 вопросов Qwen) | прямой и обратный порядки: совпали по каждому id, **0 расхождений из 20** (§8.3) |
| Захват всех слоёв, Gemma | найдены все 35 тензоров `l_out-0 … l_out-34` (§4) |
| Захват всех слоёв, Qwen | **24/24** на каждом примере, иначе строка ушла бы в `skipped` (§8.3) |
| Подмножество слоёв | `--layers step=2` → `[5, 18, 1536]`, `--layers 4,8,12` → `[5, 3, 1536]`, строки совпадают с полным прогоном `[5, 35, 1536]` (§7) |
| NaN / Inf | отсутствуют (§4, §7, §8.3) |
| Слишком длинный пример | `skipped (too long…)`, код возврата 0 (§7) |
| Возобновление | массивы восстановлены байт-в-байт (§7) |

### 3.4 Разметка правильности (`pipeline/label.py`)

**Нормализация.** Перед сравнением ответ и эталон приводятся к одному виду: нижний
регистр, без пунктуации, без артиклей (`a`/`an`/`the`), схлопнутые пробелы
(`pipeline/normalize.py`). Если так получилось пусто (например, ответ — один артикль),
применяется запасной вариант: то же самое, но артикли **не** удаляются
(`label.py`, `norm_with_fallback`). Из-за этого строки больше не уходят в «нет метки»
по причине пустой нормализации (`report.md`, §10.1).

Правила. Все считаются только для строк `status=ok` и `generated=true`.

| Колонка | Что делает (одним предложением) | Пример (реальная строка) |
|---|---|---|
| `correct_strict` | 1, если **любой** эталон встречается в ответе как целая фраза по границам слов | вопрос «A harquebus/arquebus is an early form of?», ответ `a gun`, эталон `Gun` → **1** (`audit.csv`, `bb_3033`) |

Строка `matched_strict` хранит, какой именно кусок эталона совпал с ответом. Если этот
кусок — это дословный повтор слов вопроса, то ответ по сути пересказывает вопрос, а не
отвечает на него. Таких строк среди всех единиц `strict`: **154 из 1004 = 15.3 %**
(пересчёт `labels.csv`: `correct_filtered_a != correct_strict`). Под фильтр `b` попадает
148 из 1004 = 14.7 % (`correct_filtered_b != correct_strict`).

Что показала ручная разметка этих строк:

- в `audit2` группа `filter_changed` (40 строк из пула 148): человек поставил **0 во
  всех 40 случаях** — то есть фильтр убрал **только неправильные** ответы
  (`audit2_human.csv`, пересчёт `label.py --audit2-score`);
- в `audit` три строки, которые фильтр переворачивает (`qf_2311`, `qw_9112`, `tc_1009`),

Итого проверено 43 строки из 154, и все 43 оказались ложными единицами. То есть примерно
15 % всех «правильных» ответов строгого правила — это просто эхо вопроса, и фильтр
(`correct_filtered_b`) их убирает.

### 3.7 Baseline: logprob и энтропия первого токена (шаг 4)

Самый простой способ «угадать правильность» без скрытых состояний: посмотреть на
**первый выданный токен ответа**. Два признака уже лежат в `meta.jsonl`:

- `logprobs[0]` — логарифм вероятности, которую модель дала этому токену (ближе к нулю —
  увереннее);
- `entropies[0]` — энтропия распределения по словарю в этой позиции (меньше — увереннее).

Скрипт `pipeline/baseline.py` (только `numpy`) считает AUROC/AUPRC, Brier и ECE,
подгоняет калибровку `p = sigmoid(b0 + b1·x)` **на val** и применяет её к test.

Данные: 5977 строк с меткой `correct_filtered_b` (23 `truncated` исключены); val — 1193
строки, 166 правильных (0.139), test — 1195 строк, 178 (0.149). Стыковка `meta.jsonl`
и `labels.csv` — по `row` (в `labels.csv` есть дубль `id` `bb_956` — две разные строки).

| split | признак | AUROC | AUPRC | Brier | ECE |
|---|---|---|---|---|---|
| val | `logprob` | 0.729 | 0.319 | — | — |
| test | `logprob` | 0.739 | 0.321 | — | — |
| val | `entropy` | 0.743 | 0.336 | — | — |
| test | `entropy` | 0.767 | 0.350 | — | — |
| val | `logprob`, калибр. | 0.729 | 0.319 | 0.109 | 0.012 |
| test | `logprob`, калибр. | 0.739 | 0.321 | 0.114 | 0.014 |
| val | `entropy`, калибр. | 0.743 | 0.336 | 0.107 | 0.015 |
| test | `entropy`, калибр. | 0.767 | 0.350 | 0.112 | 0.025 |
| val | сырая `exp(lp0)` | 0.729 | 0.319 | 0.118 | 0.063 |
| test | сырая `exp(lp0)` | 0.739 | 0.321 | 0.124 | 0.060 |

(95 % интервалы bootstrap — в `out/main_qwen08/baseline.json` и `report.md`, §12;

Что из этого следует:

- baseline далёк от случайного, но и не решает задачу: AUROC 0.73–0.77, AUPRC 0.32–0.35

### 3.8 Проба: логистическая регрессия по скрытым состояниям (шаг 5)

Baseline смотрел только на первое слово ответа. Проба берёт **весь вектор скрытого
состояния** (1024 числа) — отдельно для каждой точки (A или C) и каждого слоя — и учит
на train простую модель «да/нет»: L2-логистическую регрессию (`pipeline/probe.py`).

**Протокол (зафиксирован до того, как считался тест):**

1. сила регуляризации `λ` — из фиксированной сетки `{100, 300, 1000, 3000}`, выбирается
   по **среднему val AUROC по всем 48 конфигам** (24 слоя × 2 точки);
2. пара «точка + слой» — по максимуму val AUROC при выбранном `λ`;
3. тест считается **один раз** — только для победившей пары.

Данные те же: train 3589 (512 правильных), val 1193 (166), test 1195 (178); 23
`truncated` исключены.

Выбран `λ = 1000` (средние val AUROC: 100 → 0.790, 300 → 0.803, **1000 → 0.809**,
3000 → 0.804). Победила пара **точка C, слой 13**:

| split | AUROC [95 % CI] | AUPRC | Brier | ECE |
|---|---|---|---|---|
| val | 0.890 [0.861, 0.915] | 0.635 | 0.081 | 0.035 |
| **test** | **0.857 [0.825, 0.885]** | **0.593** | **0.089** | **0.019** |

Контроли: перемешанные метки на train дают test AUROC 0.490 ± 0.052 (то есть ~случайность),
слой 0 — 0.681 (A) и 0.718 (C) на test. Значит, сигнал идёт именно от глубоких слоёв,
а не от формата входа.

Что это значит:

- проба явно сильнее baseline: AUROC 0.857 против 0.739 (logprob) и 0.767 (энтропия);
  AUPRC 0.593 против 0.321 и 0.350;
- val (0.890) выше test (0.857) — ожидаемо: пара выбиралась по val, поэтому честное
  число — test, а разрыв 0.033 это «цена выбора» из 48 вариантов;
- на val точка C сильнее A (0.890 на слое 13 против 0.826 на слое 17), у C качество
  растёт до 13–14 слоя и потом падает, у A — до 17–18; полная кривая по слоям — в
  `probe_curve.csv` (тест для остальных слоёв не считался по протоколу);
- проба уже неплохо откалибрована (ECE 0.019 на test), дополнительная калибровка не нужна.

Артефакты: `out/main_qwen08/probe.json` (протокол, кривая, метрики, контроли),
`probe_curve.csv` и `probe_scores.csv`. Команда — в разделе 5, шаг 7.

### 3.9 Вторая модель: Gemma 4 E2B (шаг 7)

Тот же протокол целиком, но на другой модели — `gemma-4-E2B-it-Q4_K_M.gguf` (35 слоёв,
D=1536), тот же вход `main.jsonl` и тот же шаблон. Сначала пилот 200 (200/200 ok,
0 обрезок, 40.6 s, 4.93 ex/s), затем полный прогон: **6000/6000 ok, 0 skipped,
`truncated` 13 (0.2 %), 1258.1 s, 4.77 ex/s**, `retokenize mismatch` 32/6000 (0.5 %),
массивы `[6000, 35, 1536]`.

Что выяснилось про ответы Gemma (подробно — `report.md`, §14.2):

- 25 строк без метки: 13 `truncated` + 12 «нетривиальных» (9 пустых генераций
  нулевой длины и 3 вырожденных ответа: `}`, `?`, `\r`); у Qwen таких не было;
- 4 обрезанные строки начинаются с `<|channel>thought`, хотя `thinking: false` —
  утечка thinking-канала, причину не выясняли;
- первый токен Gemma почти всегда служебный: медиана `logprobs[0]` = −0.235, у 39.8 %
  строк вероятность первого токена > 0.9 (у Qwen — 1.3 %). Поэтому сырая вероятность
  `exp(lp0)` у Gemma бесполезна как вероятность (ECE 0.518).

Разметка: strict 0.203, relaxed 0.206, **filtered_b 0.182** — Gemma отвечает верно
чаще Qwen (0.168). Проба: λ = 1000, победила **точка C, слой 19**.

| | Qwen3.5-0.8B | Gemma 4 E2B |
|---|---|---|
| слоёв × D | 24 × 1024 | 35 × 1536 |
| доля правильных (filtered_b) | 0.168 | 0.182 |
| baseline logprob, test AUROC | 0.739 | 0.705 |
| baseline entropy, test AUROC | 0.767 | 0.712 |
| проба: точка, слой | C, 13 | C, 19 |
| проба: val AUROC | 0.890 | 0.908 |
| **проба: test AUROC** | **0.857** [0.825, 0.885] | **0.935** [0.918, 0.950] |
| проба: test AUPRC | 0.593 | 0.744 |
| контроль: слой 0 (C), test | 0.718 | 0.780 |
| контроль: перемешанные метки | 0.490 ± 0.052 | 0.521 ± 0.056 |

Наблюдения:

- лучший слой у обеих моделей — примерно на 54 % глубины (13/24 и 19/35), и в обеих
  случаях точка C лучше A;
- у Gemma тест **выше** val (0.935 против 0.908), у Qwen — ниже (0.857 против 0.890);
  причина не установлена, val и test — разные наборы вопросов;
- парное сравнение на 1189 общих тестовых строках (`compare_probes.py`): ΔAUROC в
  пользу Gemma **+0.078** [+0.048, +0.106], ΔAUPRC **+0.151** [+0.080, +0.225], все
  1000 bootstrap-ресэмплов за Gemma. Но это не чистое сравнение моделей: метка у
  каждой модели своя (правильность её ответа), и Gemma чаще права (0.182 против 0.168).

Артефакты: `out/main_gemma4e2b/` (`meta.jsonl`, `labels.csv`, `baseline.*`, `probe.*`,
`config.json`), `out/pilot_gemma4e2b/`, `out/compare_qwen08_gemma4e2b_test.json`.
Команды — в разделе 5, шаг 8.

### 3.10 Третья модель: gpt-oss-20b (шаг 8)

`gpt-oss-20b-MXFP4.gguf` — 24 слоя, D = 2880, MoE (32 эксперта). Reasoning у модели
штатно не отключается: шаблон всегда просит `Reasoning: medium`, `--no-thinking` он
игнорирует, а `--reasoning*` действуют через сэмплер, которого в инструменте нет
(генерация — greedy-argmax). Обход: `question` заменяется на готовый harmony-промпт,
обрывающийся на `<|start|>assistant<|channel|>final<|message|>`, запуск — с
`--no-template` (`pipeline/make_gptoss_prompt.py`, `report.md`, §15.1). Из-за этого
точка A — последний токен нашего промпта, а не `<|start|>assistant`; это осознанное
отклонение, иначе 64 токена уходят в канал `analysis` и всё обрезается.

Прогон: **6000/6000 ok, 0 skipped, `truncated` 27 (0.45 %), 10733.5 s, 0.56 ex/s**,
`retokenize mismatch` 21/6000 (0.3 %), массивы `[6000, 24, 2880]`. Пилот 50 строк —
46.1 s (1.08 ex/s). Замедление к концу прогона — из-за памяти машины, а не батчинга:
первые ~2100 строк шли 1.06 ex/s, свободной RAM оставалось 0.7–1 ГБ из 16.

Разметка: strict 0.494, relaxed 0.498, **filtered_b 0.490**; без метки 27 строк — все
`truncated`, пустых и вырожденных ответов нет (у Gemma были). Baseline test: logprob
0.828, entropy 0.841. Проба: λ = 3000, победила **точка C, слой 16** (67 % глубины),
val 0.9157, **test AUROC 0.9248** [0.909, 0.939], AUPRC 0.9197; контроли: перемешанные
метки 0.494 ± 0.074, слой 0 (C) 0.684.

| | Qwen3.5-0.8B | Gemma 4 E2B | gpt-oss-20b |

| слоёв × D | 24 × 1024 | 35 × 1536 | 24 × 2880 |
| доля правильных (filtered_b) | 0.168 | 0.182 | 0.490 |

- gpt-oss отделяет верный ответ от неверного почти как Gemma (0.925 против 0.935) и

### Сохранённая проба: как применить к другим данным

`probe.py` рядом с `probe.json` кладёт `probe_model.npz` (поля `w`, `mu`, `sd` и JSON
`meta`). Скор для вектора скрытого состояния `x` (float64, слой `meta["layer"]`):

```python
z = (x - mu) / sd
score = w[0] + w[1:] @ z
```

Для прогонов, сделанных до появления `probe_model.npz`, он пересобирается побайтово
тем же протоколом (та же train-выборка, стандартизация и λ; тест не пересчитывается):

```powershell
python save_probe_model.py --dir out\main_gemma4e2b
```

Проверка при пересборке: AUROC на тесте совпадает с `probe.json` до 1e-9, скоры — с
`probe_scores.csv` до 5e-9 (это округление в CSV).

## 6. Ограничения и известные особенности

- **Проверено на трёх моделях:** Gemma 4 E2B Q4_K_M (35 слоёв, D=1536),
  Qwen3.5-0.8B-BF16 (24 слоя, D=1024) и gpt-oss-20b-MXFP4 (24 слоя, D=2880).
  Выводы про инструмент для остальных моделей не проверялись (`report.md`, шапка, §8,
  §15).
- **Метки получены автоматикой и проверены выборкой.** Ручных меток всего 269:
  123 в `audit_human.csv` и 146 в `audit2_human.csv`. В случайной выборке из 100 строк
  строгое правило дало 3 ошибки, фильтр — 0; **доверительных границ для оценки шума
   в `report.md` нет — нет данных** (даны только точечные оценки 3/100 и 0/100).
- **Оценка шума — только для правил разметки**, не для самих скрытых состояний: мы
  проверяли, верно ли правило помечает ответы, а не то, насколько модель реально права.
- **Вопросы с выбором внутри** («A or B?») позволяют угадать ответ, даже не зная его:
  например, `qf_1667` «Which is the largest in area - The Sahara
  Desert or Australia?» и `tc_1007` «Who was born first, Kiefer Sutherland or Christian
  Slater?» (`audit2_human.csv`) — оба помечены правильными. **Сколько таких вопросов в
  датасете — нет данных** (не считалось).
- **Повторная токенизация сгенерированного ответа** иногда даёт не те id: в основном
  прогоне 29 из 6000 (0.5 %), в пилоте 1 из 200 (0.5 %) (`main_run1.log`;
  `report.md`, §9.4). На такие строки смотреть надо аккуратнее.
- **У Qwen 24 слоя двух типов:** 6 слоёв с полным вниманием (3, 7, 11, 15, 19, 23) и
  18 слоёв с рекуррентным (линейным) вниманием (`report.md`, §8). Кривая «по слоям»
  у такой модели, скорее всего, будет «лесенкой», а не гладкой — это надо учитывать
  при анализе.
- **Разметка целиком зависит от списка эталонов TriviaQA** (`gold` в `data/main.jsonl`):
  если в списке нет подходящего синонима, правильный ответ будет помечен неверным.
  Списки бывают длинными (в первом вопросе 24 варианта, `data/main.jsonl`).
- **Пилот и основной прогон делались на одном и том же Qwen**; пилотские 200 вопросов
  — первые 200 строк того же сэмпла (первый id совпадает: `sfq_21874`,
  `data/pilot.jsonl` и `data/main.jsonl`), поэтому пилот не является независимой
  выборкой от основного прогона.
- **`--audit-score` не умеет оценивать `audit_human.csv`** (там нет колонок `correct_*`) —
  он печатает «no scored rows» и «overall noise 0.000», что легко понять неверно.
- **Логи промежуточных прогонов Gemma и пилота Qwen не сохранялись** — их числа взяты
  из `report.md`, а не из файлов логов. Лог полного прогона Gemma был только во
  временном каталоге, его числа перенесены в `report.md`, §14.1.
- **Baseline посчитан только по первому токену ответа** (`report.md`, §12 и §14.4);
  для других позиций и токенов он не считался — нет данных. Кроме того, baseline
  оценивается по автоматической метке `correct_filtered_b`, шум которой сам известен
  лишь по выборкам (см. выше).
- **Проба считается с одним тестовым замером:** λ и пара «точка + слой» выбирались по
  val, тест считался один раз для победителя (`report.md`, §13 и §14.5). AUROC на тесте
  для остальных слоёв и для точки A не считался — это сознательное ограничение
  протокола, а не пропуск. 1024–1536 признаков на ~3600 строк train — модель маленькая
  и сильно регуляризованная (`λ = 1000`); на других моделях результат может отличаться.
- **Ответы Gemma местами деградируют:** 9 генераций нулевой длины и 3 вырожденных
  ответа (`}`, `?`, `\r`), 4 обрезанные строки начинаются с `<|channel>thought` при
  `thinking: false` (`report.md`, §14.2). Причины не исследованы — это «нет данных»,
  а не объяснение. Такие строки исключены из метрик (25 null из 6000).
- **Qwen и Gemma сравнивались не на общей метке:** у каждой модели своя правильность
  ответа, поэтому ΔAUROC в пользу Gemma (+0.078) отражает и разную долю правильных
  ответов (0.182 против 0.168), и разное качество проб (`report.md`, §14.6).
- **У Gemma тест выше val** (0.935 против 0.908), у Qwen — ниже (0.857 против 0.890);
  причина не установлена — нет данных.
- **У gpt-oss точка A другая:** промпт обрывается на `<|start|>assistant<|channel|>final<|message|>`,
  поэтому A — последний токен нашего сообщения, а не `<|start|>assistant`, как в
  определении из `AGENTS.md`. Без этого reasoning съедает весь бюджет токенов
  (`report.md`, §15.1). Сравнивать A у gpt-oss с A у Qwen/Gemma нужно с этой оговоркой.
- **Скорость полного прогона gpt-oss зависела от свободной RAM:** 1.06 ex/s в начале,
  0.4–0.6 ex/s во второй половине (свободно 0.7–1 ГБ из 16), итог 0.56 ex/s. Отдельного
  замера одиночного режима на всех 6000 строках нет — ускорение ×2.9 оценено по 200
  строкам (`report.md`, §15.7).
- **AUPRC между моделями напрямую не сравнивать:** доля правильных ответов у gpt-oss
  0.49 против 0.17–0.18 у малых моделей, поэтому AUPRC 0.92 высок по построению.
  Сравнимы в первую очередь AUROC и контроли.
- **Первый полный прогон gpt-oss (5596 s) недействителен:** инструкция в промпте стояла
  дважды, результат лежит в `out/main_gptoss20b_dupinstr/` и в отчёты не входит
  (`report.md`, §15.2.1). Неполный прогон `out/main_gptoss20b/` (325/6000, остановлен
  вручную) тоже не используется.
- **Перенести обученную пробу с одной модели на другую «в лоб» нельзя.** Проба —
  линейная по вектору скрытого состояния, а размерности у моделей разные: Qwen D=1024,
  Gemma D=1536, gpt-oss D=2880. Вектор признаков Qwen (1024) не умножить на веса
  Gemma-пробы (1536). Сами веса теперь сохраняются рядом с `probe.json` в
  `probe_model.npz` (`w`, `mu`, `sd`), но это не снимает несовпадения размерностей.
  Скрипт `pipeline/cross_model_test.py` (не в git) делал именно невозможное —
  `np.dot(hs_qwen, w_gemma)` и `probe['coefficients']`; результат не запускался.
  Корректные варианты: (а) прогнать Gemma на ответах Qwen и применить Gemma-пробу к
  состояниям Gemma (это перенос на другой текст, а не на другое пространство) или
  (б) отдельно учить линейное выравнивание пространств; ни то, ни другое не запускалось.

## 8. Глоссарий

| Термин | Значение |
|---|---|
| **GGUF** | формат файла с весами языковой модели, формат ввода для llama.cpp |
| **llama.cpp** | библиотека-движок для запуска таких моделей; наш инструмент написан поверх её |
| **токен** | кусочек слова, на который модель делит текст; модель считает счётчики по токенам, а не по буквам |
| **промпт** | часть входа модели до ответа: инструкция + вопрос (здесь уже отрисованный чат-шаблоном) |
| **чат-шаблон** | служебная разметка вида `<|im_start|>user … <|im_end|> <|im_start|>assistant`, которую модель сама задала в GGUF; применяется флагом, отключается `--no-template` |
| **токен конца реплики (EOG)** | специальный токен «конец ответа»; в метки и в точку C он не попадает |
| **скрытое состояние** | вектор чисел на выходе слоя в данной позиции — «мысли модели» в этот момент |
| **слой** | один из последовательных вычислительных блоков модели |
| **тензор** | массив чисел фиксированной формы, то, что считает модель |
| **`l_out-N`** | имя тензора «выход N-го слоя»; читаем его строку для позиций A и C |
| **колбэк `cb_eval`** | функция, которую llama.cpp вызывает по ходу вычислений; в ней мы и достаём состояния |
| **батч / ubatch** | группа примеров, обрабатываемых за один проход; здесь `n_batch = n_ubatch = max_len`, поэтому весь пример целиком проходит одним ubatch |
| **точка A** | последний токен промпта после чат-шаблона; состояние, из которого выдаётся первый токен ответа |
| **точка C** | последний содержательный токен ответа (без EOG) |
| **метка correct** | 1/0 — верен ли ответ модели относительно эталона |
| **strict / relaxed** | строгое и ослабленное правила выставления метки (см. 3.4) |
| **фильтр (filtered_a / filtered_b)** | надстройка над strict, убирающая ложные единицы из ответов, повторяющих вопрос |
| **`truncated`** | ответ обрезан из-за бюджета токенов; такие строки в разметку не идут |
| **`logprob`** | логарифм вероятности, которую модель дала выбранному токену; чем выше, тем увереннее модель |
| **энтропия** | мера размазанности вероятностей по словарю: высокая — «модель сама не знает» |
| **baseline** | наивная оценка для сравнения с пробой (здесь — logprob первого токена) |
| **проба** | разведочный прогон простой модели (логистической регрессии) на признаках-состояниях |
| **логистическая регрессия** | простейшая модель «да/нет»: линейная комбинация признаков → число от 0 до 1 |
| **AUROC** | доля пар «правильный ответ оценён выше, чем неправильный»; 0.5 — случайность, 1.0 — идеал |
| **validation (val) / test** | выборки для настройки и для финальной оценки; слой выбираем по val, тест считаем один раз |
| **сплит** | распределение вопросов по train/val/test; здесь — по группам эталонов |
| **`fp` / `fn`** | ложная единица (авто=1, человек=0) и ложный пропуск (авто=0, человек=1) |
| **seed** | число, фиксирующее случайный выбор, чтобы прогон можно было повторить |
| **retokenize mismatch** | случай, когда повторная токенизация текста ответа даёт другие id, чем при генерации |
