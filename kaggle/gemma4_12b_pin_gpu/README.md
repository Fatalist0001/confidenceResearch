# Ядро: наш hs на пине, 1 GPU против 2 GPU (gemma-4-12B)

Ядро `odinodinodin/hs-gemma4-12b-pin-gpu`, 2026-11-01, `NvidiaTeslaT4` (2 × T4),
33.4 мин, **0.56 ч квоты** (всего 3.95 из 30 ч). Собирает **наш** `llama-hidden-states`
на пине `d4cff114c` (как в реальных прогонах), качает 12B Q4_K_M и задаёт одни и те же
8 простых вопросов в двух режимах: `-sm none` на одной карте и `-sm layer` на двух.

## Результат: пин сломан сам по себе, разбиение по GPU ни при чём

| режим | correct | примеры ответов |
|---|---|---|
| `-sm none`, 1 GPU | **0/8** | `The answer is **no**.` · `The correct answer is **The** (as in **The** (as in …` |
| `-sm layer`, 2 GPU | **0/8** | **те же самые строки, дословно** |

Ответы в двух режимах совпадают побайтово (включая обрезанные на 60–79 токенах), то есть
вывод детерминирован и от числа GPU не зависит. Пилот тех же 200 строк на одной карте:
200/200 ok, `truncated` 81 (40.5 %) — та же картина, что и в неудачном полном прогоне.

Для сравнения, тот же вопрос про Гамлета:

| движок | ответ |
|---|---|
| пин `d4cff11` (1 и 2 GPU) | `The answer is **no**.` |
| master `dde879b`, ручной промпт | `William Shakespeare` |

## Что это значит

- **Версия llama.cpp** — единственная оставшаяся причина. Промпт канонический
  (см. `kaggle/gemma4_12b_debug/README.md`), модель и квант исправны (8/8 на master),
  число GPU не влияет.
- Пин `d4cff114c` выпущен **2026-07-03**, а `gemma-4-12B-it` — **2026-07-09**, то есть
  инструмент старше модели. Между пином и master по gemma4 прошли `163a40796`
  (2026-09-04), `97e4ca735` (2026-09-14, «fix incorrect uses of `get_key_or_arr`» — а у
  12B массивы `head_count_kv` и `sliding_window_pattern` по слоям), `344846b4f`
  (2026-10-30, `token_embd` до tied output — у 12B `tie_word_embeddings = true`),
  `0138937e3` (2026-10-31, rope в слоях с общим KV).
- Дальше нужен перенос `hidden-states.cpp` на новый common API и пересборка; 12B на пине
  получить нельзя никакими флагами.
