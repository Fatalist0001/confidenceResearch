# llama-hidden-states: уверенность языковой модели по скрытым состояниям

Этот проект проверяет простой вопрос:

> Можно ли по одному внутреннему вектору языковой модели понять, будет ли её ответ
> правильным?

Для каждого вопроса инструмент извлекает скрытые состояния всех доступных слоёв GGUF-модели
в двух точках ответа. Затем для каждого слоя обучается простая логистическая регрессия —
**линейная проба**. Её качество сравнивается с более очевидным baseline: вероятностью и
энтропией первого токена ответа.

Главный результат: один вектор из середины сети действительно хорошо ранжирует правильные
и неправильные ответы. На большинстве полноценных прогонов test AUROC лежит примерно в
диапазоне **0.86–0.94**. При этом увеличение модели выше 4B почти не улучшает эту
однослойную линейную пробу, хотя сами ответы становятся заметно правильнее.

> **Состояние на 2026-11-02:** выполнено 15 полных прогонов семи семейств. Для Gemma 4
> 12B готовы состояния, разметка и baseline, но probe отложена. Для
> LFM2.5-1.2B-Thinking запланирован отдельный эксперимент с ограниченным reasoning budget.

> **Для агента и для быстрого старта:** порядок работы, какие прогоны цитировать,
> заблокированные действия и рецепты лежат в `docs/START-HERE.md`; установка с нуля —
> `docs/SETUP.md`; машинночитаемый реестр — `RUNS.json`; флаги по моделям —
> `profiles.json`; рабочий цикл — `scripts/run.ps1`. Научная часть ниже и в `report.md`
> остаётся подробной и не заменяется этими файлами.

## 1. Коротко о результате

Пайплайн одинаков для всех моделей:

```text
вопросы → ответы модели → автоматические метки 0/1
        → скрытые состояния A/C всех слоёв
        → логистическая проба каждого слоя
        → выбор по validation
        → один финальный замер на test
```

Основные наблюдения:

1. **Скрытые состояния информативнее первого токена.**
   Проба обычно даёт AUROC выше baseline на 0.04–0.22.

2. **Почти всегда побеждает точка C.**
   То есть полезнее состояние после сформированного ответа, чем состояние перед первым
   токеном ответа.

3. **Лучший слой находится около середины сети.**
   Типичная глубина победителя — 50–57% от числа слоёв. Соседние слои часто образуют
   широкое плато и отличаются всего на 0.004–0.01 AUROC.

4. **Больше знаний не обязательно означает лучшую пробу.**
   В серии Qwen правильность выросла с 0.118 до 0.570, а probe AUROC вышел на плато уже
   около 4B: 0.871 → 0.886 → 0.918 → 0.917.

5. **Потолок текущего признака — примерно 0.92–0.94.**
   Его достигли разные семейства: Gemma, Qwen и gpt-oss. Вероятно, ограничение задаёт не
   размер модели, а сам признак: один вектор одного слоя и линейный классификатор.

6. **Точный номер слоя не надо переоценивать.**
   Например, у LFM2.5-2.6B слои C/15–20 отличаются примерно на 0.004 AUROC. Устойчивый
   вывод — «середина сети», а не «слой 17 особенный».

## 2. Что именно измеряется

### 2.1. Модель и токены

Модель получает не строку целиком, а последовательность **токенов** — числовых id частей
слов, знаков и специальных маркеров.

Перед токенизацией вопрос оформляется **чат-шаблоном** из GGUF. Шаблон добавляет служебные
маркеры пользователя и ассистента. Некоторые модели также требуют начальный токен BOS
(`beginning of sequence`). Токен EOG (`end of generation`) завершает ответ.

Ведущий BOS важен: старый пакетный режим терял его у моделей с
`add_bos_token=true`. На Gemma 4 12B это почти полностью разрушило ответы. Сейчас BOS
добавляется так же, как в `llama-cli`.

### 2.2. Скрытое состояние

После каждого слоя у каждого токена есть вектор чисел:

```math
x_{i,l,t} \in \mathbb{R}^{D},
```

где:

- $i$ — номер примера;
- $l$ — слой;
- $t$ — позиция токена;
- $D$ — размерность скрытого состояния.

Этот вектор — промежуточное внутреннее представление модели. Он не является готовой
вероятностью правильности. Проба проверяет, можно ли линейно извлечь из него такой сигнал.

### 2.3. Точки A и C

Для каждого слоя сохраняются два вектора:

- **A** — состояние последнего токена уже отрисованного промпта. Из него модель предсказывает
  первый токен ответа.
- **C** — состояние последнего содержательного токена ответа. EOG и конец реплики в C
  не входят.

Схематично:

```text
[BOS] ... вопрос ... [assistant marker]  ответ ... последний токен [EOG]
                                      A                           C
```

Генерация ответа и извлечение состояний выполняются разными проходами. Перед проходом
состояний память модели очищается, затем декодируется точная последовательность
`prompt + answer`.

## 3. Данные и разметка правильности

### 3.1. Набор вопросов

Используется `mandarjoshi/trivia_qa`, конфигурация `rc.nocontext`, исходный split
`validation`.

После фильтрации и воспроизводимой выборки получено 6000 вопросов:

| split | строк | назначение |
|---|---:|---|
| train | 3600 | обучение пробы |
| val | 1200 | выбор λ, точки и слоя; калибровка |
| test | 1200 | один финальный замер |

Разбиение выполняется по группе нормализованного основного ответа. Хеш
`SHA-256(seed:group)` с seed 42 детерминированно назначает группу в train/val/test. Поэтому
вопросы с одним и тем же основным ответом не должны попадать в разные splits.

Каждый вопрос заканчивается инструкцией:

```text
Answer with just the answer, no explanation.
```

`data/pilot.jsonl` содержит первые 200 строк для проверки модели перед дорогим полным
прогоном. Пилот не является независимой тестовой выборкой.

Подготовка основного набора:

| шаг | строк осталось | что произошло |
|---|---:|---|
| исходный TriviaQA validation | 17 944 | `rc.nocontext`, без текста статьи |
| дедупликация вопроса | 9 961 | одинаковые нормализованные вопросы объединены |
| фильтр длины и эталонов | 9 947 | удалены вопросы длиннее 300 символов и строки без ответа |
| воспроизводимая выборка | 6 000 | сохранена пропорция 60/20/20 |

Внутри каждого split порядок исходных строк сохраняется. Выборка делается стандартным
Python RNG с seed 42. Список id и параметры подготовки записаны в `main_meta.json`.

Одна строка JSONL выглядит упрощённо так:

```json
{
  "id": "sfq_21874",
  "question": "What name ...?\nAnswer with just the answer, no explanation.",
  "gold_main": "HYPERLINK",
  "gold": ["hyperlink", "hypertext link", "link"],
  "split": "train"
}
```

Неизвестные поля входной строки инструмент копирует в `meta.jsonl`. Это позволяет
сохранить `gold`, `split` и будущие дополнительные метаданные без изменения C++-кода.

В `main.jsonl` есть два разных вопроса с одинаковым id `bb_956`. Это известная особенность
источника, а не повреждение данных. Сопоставлять строки нужно по `row` или по паре
`(id, номер вхождения)`, а не по одному id.

### 3.2. Нормализация текста

Для сравнения ответа модели с эталонами текст:

1. переводится в нижний регистр;
2. очищается от ASCII-пунктуации;
3. из него удаляются артикли `a`, `an`, `the`;
4. повторные пробелы объединяются.

Если такая нормализация даёт пустую строку, используется запасной вариант, который
сохраняет артикли.

### 3.3. Метки

У каждого вопроса есть основной ответ `gold_main` и список допустимых вариантов `gold`.

| колонка | правило |
|---|---|
| `correct_strict` | токены одного из эталонов встречаются в ответе подряд |
| `correct_relaxed` | strict, либо все слова многословного эталона встречаются в любом порядке, либо совпадает простая форма без конечного `s` |
| `correct_filtered_a` | strict, но совпадение отбрасывается, если та же фраза уже была в вопросе |
| `correct_filtered_b` | как A, но основной эталон `gold_main` не отбрасывается только за присутствие в вопросе |
| `correct` | исторический alias для `correct_strict` |

Все baseline и пробы обучаются на **`correct_filtered_b`**. Эта метка уменьшает число
ложных единиц, когда модель просто повторяет вариант ответа из вопроса.

Пример strict-совпадения:

```text
answer: "It was written by William Shakespeare."
gold:   "William Shakespeare"
```

После нормализации эталон встречается как непрерывная последовательность токенов, поэтому
`correct_strict=1`, даже если ответ длиннее эталона.

Пример причины фильтра:

```text
question: "Was it France or Germany?"
answer:   "France"
gold_main: "Germany"
gold alias list accidentally contains "France"
```

Strict может дать единицу из-за alias, уже напечатанного в вопросе. `filtered_b`
обнулит такое совпадение, если совпавший alias не равен основному эталону.

Метка остаётся пустой (`null`), если:

- строка не имеет `status=ok`;
- ответ не был сгенерирован;
- ответ обрезан по лимиту (`truncated=true`);
- нормализованный ответ пуст.

Такие строки исключаются из baseline и probe. Поэтому колонка `valid` в итоговых таблицах
может быть меньше 6000.

### 3.4. Насколько можно доверять меткам

Разметка автоматическая, а не ручная. Она проверялась двумя аудитами — всего 269 ручных
примеров. На случайной выборке 100 строк strict дала 3 ошибки, а дополнительный фильтр —
0 ошибок. Это полезная проверка, но не полноценная оценка шума на всём наборе.

Аудиты отвечают только на вопрос «верно ли сработало правило сопоставления текста».
Они не дают независимой экспертной оценки фактической правильности всех ответов модели.
Например, если нужного синонима нет в списке TriviaQA, автоматическая метка может быть
нулём даже для содержательно правильного ответа.

Вопросы с вариантами внутри текста также сложнее интерпретировать. Модель может повторить
один из вариантов без знания факта, поэтому `filtered_b` уменьшает, но не устраняет все
такие случаи.

## 4. Как извлекаются скрытые состояния

### 4.1. Инструмент

`llama-hidden-states` — отдельный пример поверх публичного API llama.cpp. Ядро llama.cpp
не изменяется.

Во время построения вычислительного графа llama.cpp вызывает callback `cb_eval`.
Инструмент запрашивает только тензоры `l_out-N` — выходы слоёв — и копирует строки,
соответствующие A и C.

Обычно один слой даёт один `l_out`. Исключение — Nemotron 3 Nano: из 42 архитектурных
слоёв `l_out` доступен только на 17. Инструмент сначала делает пробный decode, обнаруживает
доступные тензоры и сохраняет только их.

Callback llama.cpp работает в двух фазах:

1. `ask=true`: инструмент отвечает, нужен ли текущий тензор. `true` возвращается только
   для выбранных `l_out-*`, чтобы не синхронизировать все промежуточные тензоры.
2. `ask=false`: тензор уже вычислен. Инструмент читает нужную строку A или C и всегда
   разрешает графу продолжиться.

Буферы A/C выделяются один раз на модель и переиспользуются. Во время генерации callback
отключён, поэтому каждый слой не копируется на каждом новом токене.

### 4.2. Важные инварианты

- Промпт и ответ токенизируются раздельно, затем id склеиваются.
- Специальные токены разрешены (`parse_special=true`).
- BOS добавляется токенизатором, если модель его требует.
- `n_batch = n_ubatch = max_len`, поэтому пример проходит одним ubatch и строка тензора
  совпадает с позицией токена.
- Слишком длинная строка не аварийно завершает прогон: она получает `status=skipped`.
- В состояниях пропущенной строки остаются нули.
- Генерация сейчас использует raw greedy argmax. Полноценная sampler chain llama.cpp,
  temperature, top-k и repeat penalty не применяются.

Последний пункт важен для LFM3 и gpt-oss: поведение нашего генератора может отличаться
от `llama-cli` и LM Studio даже на тех же весах.

### 4.3. Почему генерация и состояния считаются раздельно

Первый проход генерирует ответ токен за токеном и сохраняет:

- текст ответа;
- id выбранных токенов;
- logprob и энтропию для каждого содержательного токена;
- причину остановки: EOG, лимит, ошибка decode.

После генерации текст ответа токенизируется отдельно теми же правилами специальных
токенов. Если новые id не совпали с id генерации, увеличивается счётчик
`retokenize mismatch`. Это возможно из-за неоднозначного декодирования пробелов и
специальных фрагментов.

Перед вторым проходом KV/memory очищается. Затем `prompt + answer` проходит одним decode,
и A/C считываются из одного и того же вычислительного графа. Такой дизайн дороже одного
прохода, но делает определения точек явными и одинаковыми для ответов, заданных во входе,
и ответов, сгенерированных моделью.

EOG не добавляется в ответный вектор C. Если содержательного ответа нет, A и C могут
совпасть; пустые и обрезанные ответы затем исключаются разметкой.

### 4.4. Формы массивов

Пакетный режим записывает:

```text
hidden_a.npy: float16 [N, L, D]
hidden_c.npy: float16 [N, L, D]
```

где $N$ — число строк, $L$ — число выбранных доступных слоёв, $D$ — размерность модели.

Одиночный исторический режим v1 сохраняет `[L, D]`; его поведение заморожено.

Файлы `.npy` создаются сразу полного ожидаемого размера. Заголовок хранит dtype и форму,
после чего каждая строка записывается по смещению `row`. Это позволяет возобновить
частичный прогон и сохраняет нули для skipped-строк.

`float16` уменьшает объём вдвое относительно float32. Probe при чтении переводит один
слой нужных строк в float64; весь трёхмерный массив одновременно в RAM не загружается.

### 4.5. Остальные выходы

| файл | содержимое |
|---|---|
| `meta.jsonl` | id, row, split, ответ, позиции A/C, статус, logprob и entropy токенов |
| `config.json` | модель, слои, размеры, шаблон, thinking, версия llama.cpp, определения точек |
| `labels.csv` | strict/relaxed/filtered-метки |
| `baseline.json` | метрики первого токена |
| `probe.json` | выбранные λ, точка, слой, метрики и контроли |
| `probe_curve.csv` | train/val-качество каждого слоя, точки и λ |
| `probe_scores.csv` | score/probability для val и test |
| `probe_model.npz` | переносимые веса выбранной пробы |
| `verify.json` | результат проверки целостности каталога |

Большие `.npy` не хранятся в Git.

### 4.6. Возобновление и `row`

`meta.jsonl` — журнал уже обработанных строк. При повторном запуске в тот же каталог
инструмент пропускает известные id и пишет состояния по полю `row`. Поэтому resume может
восстановить недописанный массив.

Однако финальные каталоги считаются неизменяемыми. Повторный запуск поверх полного
каталога опасен: одинаковый id `bb_956`, изменившийся вход или другая версия модели могут
создать трудно обнаруживаемую смесь результатов. Для каждого эксперимента используется
новый тег.

### 4.7. Батчирование строк

Флаг `--batch-rows K` объединяет несколько независимых последовательностей в decode.
Каждая строка получает собственный `seq_id`, локальные позиции и EOS-padding. Это сильно
ускорило gpt-oss-20b (`K=8`), но для малых моделей выигрыш был около 1.2 раза.

Батч и одиночный проход могут немного различаться численно из-за порядка операций,
особенно в MoE. Проверено, что между строками нет утечки, а повторные одинаковые batch-run
детерминированы. Для обычных локальных прогонов используется `batch_rows=1`; исключение —
gpt-oss.

## 5. Baseline: logprob и энтропия

### 5.1. От логитов к вероятностям

Для очередного токена модель выдаёт **логиты** $a_v$ для каждого токена словаря $v$.
Softmax превращает их в распределение вероятностей:

```math
p_v = \frac{e^{a_v}}{\sum_u e^{a_u}}.
```

На практике из всех логитов вычитается максимум, чтобы экспоненты не переполнялись.
Если $m=\max_v a_v$, вычисляется эквивалентное выражение
$p_v=e^{a_v-m}/\sum_u e^{a_u-m}$.

### 5.2. Logprob выбранного токена

Если модель выбрала токен $t$, его logprob:

```math
\ell_t = \log p_t.
```

Он всегда не больше нуля. Чем ближе к нулю, тем выше вероятность выбранного токена.
Во всех формулах `log` — натуральный логарифм.

Примеры:

| вероятность токена | logprob |
|---:|---:|
| 0.90 | −0.105 |
| 0.50 | −0.693 |
| 0.10 | −2.303 |

Разница logprob аддитивна: сумма logprob последовательности равна логарифму произведения
условных вероятностей её токенов. В этом проекте baseline использует только первый
токен, а не сумму по ответу.

Сырая вероятность первого токена:

```math
p_{\mathrm{raw}} = e^{\ell_0}.
```

### 5.3. Энтропия

Энтропия всего распределения первого токена:

```math
H_0 = -\sum_v p_v \log p_v.
```

Низкая энтропия означает, что распределение сосредоточено на небольшом числе токенов.
Для ранжирования используется score $-H_0$: чем он выше, тем модель увереннее.

Logprob и энтропия отвечают на разные вопросы:

- logprob: насколько вероятен именно выбранный токен;
- entropy: насколько распределение в целом размазано по альтернативам.

Модель может выбрать довольно вероятный токен, но иметь несколько почти равных
альтернатив — тогда logprob относительно высокий, а энтропия тоже высокая.

### 5.4. Что именно сравнивается

Baseline использует только первый токен содержимого ответа:

- logprob score: $\ell_0$;
- entropy score: $-H_0$.

У некоторых моделей первый токен служебный или почти постоянный. Тогда абсолютная
вероятность плохо откалибрована, но ranking всё ещё может быть полезен.

Например, если ответы часто начинаются с пробела, кавычки или фиксированного маркера,
$e^{\ell_0}$ измеряет уверенность в этом маркере, а не в факте. Энтропия всё же может
различаться, потому что учитывает весь словарь.

### 5.5. Калибровка baseline

На validation обучается одномерная логистическая калибровка:

```math
\hat p = \sigma(b_0 + b_1 q), \qquad
\sigma(z)=\frac{1}{1+e^{-z}},
```

где $q=-\ell_0$ или $q=-H_0$. Коэффициент $b_1$ сам выбирает правильное
направление. Калибровка меняет вероятности, но не должна менять AUROC, если преобразование
монотонно.

Коэффициенты подбираются только на val методом IRLS. На test они не переобучаются.

### 5.6. Как читать baseline.json

Для каждого split записываются несколько вариантов:

| ключ | score для ranking | probability для Brier/ECE |
|---|---|---|
| `logprob` | $\ell_0$ | нет |
| `entropy` | $-H_0$ | нет |
| `logprob_calibrated` | калиброванная вероятность | она же |
| `entropy_calibrated` | калиброванная вероятность | она же |
| `logprob_raw_prob` | $\ell_0$ | $e^{\ell_0}$ |

AUROC/AUPRC у score и его монотонной калибровки должны совпадать. Brier/ECE имеют смысл
только для probability. Высокий AUROC вместе с плохим ECE означает: модель правильно
ранжирует ответы, но её численные вероятности нельзя воспринимать буквально.

## 6. Как обучается проба

### 6.1. Признак

Для фиксированной точки $P \in \{A,C\}$ и слоя $l$ признак одного вопроса:

```math
x_i = x_{i,l,P} \in \mathbb{R}^{D}.
```

Каждая пара «точка + слой» обучается отдельно. Слои не склеиваются.

### 6.2. Стандартизация

Среднее и стандартное отклонение считаются только на train:

```math
\mu_j = \frac{1}{n}\sum_i x_{ij}, \qquad
s_j = \sqrt{\frac{1}{n}\sum_i (x_{ij}-\mu_j)^2} + 10^{-8}.
```

После этого:

```math
z_{ij}=\frac{x_{ij}-\mu_j}{s_j}.
```

Те же $\mu$ и $s$ применяются к val и test. Это предотвращает утечку информации из
будущих splits.

### 6.3. Логистическая регрессия

Проба вычисляет линейный score:

```math
r_i = w_0 + \sum_{j=1}^{D} w_j z_{ij},
```

и вероятность:

```math
\hat p_i = \sigma(r_i).
```

Веса минимизируют логистическую ошибку с L2-регуляризацией:

```math
\mathcal{L}(w) = -\sum_i \left[y_i \log(\hat p_i) + (1-y_i)\log(1-\hat p_i)\right] + \frac{\lambda}{2}\sum_{j=1}^{D}w_j^2
```

Смещение $w_0$ не регуляризуется. Оптимизация выполняется Newton/IRLS — методом
итеративно перевзвешенных наименьших квадратов; длина одного шага ограничена для
устойчивости.

Важно: loss суммируется, а не усредняется. Поэтому численные значения λ относятся именно
к этой реализации.

Если добавить к $Z$ колонку единиц и обозначить расширенную матрицу через $X$, один шаг
использует:

```math
p = \sigma(Xw), \qquad W_i = \max\left(p_i(1-p_i), 10^{-6}\right).
```

```math
g = X^{\mathsf{T}}(y-p)-\lambda Rw,
\qquad
H = X^{\mathsf{T}}WX+\lambda R.
```

Здесь $R$ — диагональная матрица с нулём для intercept и единицами для остальных весов.
Решается $H\Delta=g$, затем $w\leftarrow w+\Delta$. Норма шага ограничивается значением
2.0. Максимум — 40 итераций, остановка — норма шага меньше $10^{-6}$.

Классы не перевзвешиваются. Поэтому логистические вероятности чувствительны к base rate,
но AUROC сравнивает порядок scores и гораздо меньше зависит от доли единиц.

L2-регуляризация нужна потому, что $D$ достигает 4096 при примерно 3600 train-строках.
Без штрафа отдельные координаты могли бы получить огромные веса и идеально описать train,
но плохо работать на новых вопросах.

### 6.4. Как выбираются λ, точка и слой

Сетка регуляризации фиксирована:

```math
\lambda \in \{100, 300, 1000, 3000\}.
```

Порядок выбора:

1. Для каждого λ обучаются все доступные слои обеих точек A и C.
2. Для λ считается средний val AUROC по всем этим конфигурациям.
3. Берётся λ с максимальным средним val AUROC.
4. При выбранном λ берётся одна пара «точка + слой» с максимальным val AUROC.
5. Только после этого один раз считается test.

Test не используется для выбора слоя и λ. Перевыбирать слой по test запрещено.

После выбора конфигурация заново обучается на том же train с теми же λ, $\mu$ и $s$.
Val не добавляется в train: он остаётся выборкой для выбора и калибровки. Это уменьшает
эффективный объём обучения, но делает протокол проще и исключает скрытое использование
test.

`probe_curve.csv` хранит результаты всех точек, слоёв и λ на train/val. По нему можно
смотреть форму кривой и ширину плато, но нельзя выбирать новый слой после просмотра test.

### 6.5. Калибровка пробы

Основная вероятность равна $\sigma(r)$. Дополнительно на val обучается Platt scaling:

```math
\hat p_{\mathrm{Platt}} = \sigma(c_0 + c_1 r).
```

Он нужен для Brier/ECE, но не для выбора слоя.

### 6.6. Переносимая проба

`probe_model.npz` хранит `w`, `mu`, `sd` и описание точки/слоя. Применение:

```math
z = \frac{x-\mu}{sd}, \qquad
r=w_0+w_{1:}^{\top}z.
```

Размерность $D$ должна совпадать. Даже одинаковая размерность разных семейств не означает,
что их пространства ориентированы одинаково: перенос Gemma E4B ↔ Qwen 4B при $D=2560$
оказался хуже случайного.

Компоненты $w$ показывают направление линейного разделения в стандартизованном
пространстве, но не дают причинного объяснения работы нейрона. Большой коэффициент может
компенсировать коррелированные координаты и не означает, что одна координата сама по себе
«кодирует правильность».

### 6.7. Контроли

Для каждой выбранной пробы считаются два контроля:

- **shuffled labels** — train-метки случайно перемешиваются. Ожидание: test AUROC около
  0.5;
- **layer 0** — проба на самом раннем доступном слое. Обычно она заметно хуже середины.

Если shuffled заметно выше 0.5 или слой 0 неожиданно побеждает, результат требует
дополнительной проверки.

Shuffled-контроль повторяется пять раз с разными перестановками одного фиксированного RNG.
В отчёт записываются среднее и sample standard deviation test AUROC. Случайные отклонения
около 0.5 ожидаемы, особенно если положительных строк мало.

## 7. Метрики и доверительные интервалы

### 7.1. Base rate

Доля положительных меток:

```math
\pi = \frac{1}{n}\sum_i y_i.
```

В таблицах это доля правильных ответов `filtered_b`.

### 7.2. AUROC

AUROC — вероятность, что случайный правильный ответ получит score выше случайного
неправильного:

```math
\mathrm{AUROC} =
\frac{1}{n_+n_-}
\sum_{i:y_i=1}\sum_{j:y_j=0}
\left[\mathbf{1}(r_i>r_j)+\frac12\mathbf{1}(r_i=r_j)\right].
```

- 0.5 — случайное ранжирование;
- 1.0 — идеальное;
- AUROC не требует откалиброванных вероятностей.

При одинаковых scores пара даёт 0.5. В коде используется эквивалентная rank-формула с
усреднёнными рангами ties. Если AUROC меньше 0.5, направление score фактически обращено;
само по себе это не означает отсутствие информации, но для заранее определённого score
такой результат считается плохим.

Простой пример: scores правильных ответов `[0.9, 0.6]`, неправильных `[0.7, 0.2]`.
Из четырёх пар правильный score выше в трёх, поэтому AUROC = 3/4 = 0.75.

### 7.3. AUPRC

AUPRC здесь реализована как average precision с группировкой одинаковых scores:

```math
P=\frac{TP}{TP+FP}, \qquad
R=\frac{TP}{TP+FN}.
```

где TP — правильные ответы, поставленные выше порога; FP — неправильные ответы выше
порога; FN — правильные ответы ниже порога.

```math
\mathrm{AUPRC} = \sum_k (R_k-R_{k-1})P_k.
```

где $P_k$ и $R_k$ — precision и recall после очередного порога.

AUPRC сильно зависит от base rate. Поэтому AUPRC моделей с разной долей правильных
ответов нельзя сравнивать так же прямо, как AUROC.

У случайного ranking ожидаемая AUPRC примерно равна base rate. Поэтому AUPRC 0.75 очень
сильна при 10% правильных, но может быть умеренной при 70% правильных.

### 7.4. Brier score

Средняя квадратичная ошибка вероятности:

```math
B = \frac{1}{n}\sum_i(\hat p_i-y_i)^2.
```

Меньше — лучше. Brier одновременно зависит от ранжирования и калибровки.

Brier лежит от 0 до 1. Идеальные вероятности дают 0. Постоянный прогноз, равный base rate,
является полезным калибровочным ориентиром, но не умеет ранжировать строки.

### 7.5. ECE

Expected Calibration Error делит вероятности на 10 равных интервалов:

```math
\mathrm{ECE} =
\sum_{b=1}^{10}\frac{|B_b|}{n}
\left|a_b-c_b\right|.
```

Здесь $a_b$ — фактическая доля единиц в bin, $c_b$ — средняя предсказанная вероятность.
Меньше — лучше. ECE зависит от выбранного числа bins и менее устойчива, чем AUROC.

Например, если в bin средняя вероятность 0.8, а правильными оказались 60% строк, вклад
этого bin до умножения на его долю равен 0.2. Пустые bins пропускаются.

### 7.6. Bootstrap 95% CI

Для val/test строки 1000 раз выбираются с возвращением. Для каждого bootstrap-набора
метрика считается заново. Интервал — процентили 2.5% и 97.5%.

При сравнении двух моделей используется **парный bootstrap**: выбираются одни и те же
вопросы, но у каждой модели остаются её собственные ответ, метка и score.

Если интервал разницы AUROC включает ноль, данных недостаточно, чтобы заявить различие.

Bootstrap показывает вариативность из-за конечного набора вопросов. Он не учитывает
ошибки автоматической разметки, смену prompt, другую версию llama.cpp и случайность
обучения новой модели.

### 7.7. Пример чтения набора метрик

Для LFM2.5-1.2B на test:

```text
base rate = 0.179
AUROC     = 0.881
AUPRC     = 0.688
Brier     = 0.094
ECE       = 0.034
```

Это означает:

- правильных ответов около 18%;
- в 88.1% случайных пар «правильный–неправильный» правильный имеет больший score;
- average precision 0.688 значительно выше случайного ориентира около 0.179;
- средняя квадратичная ошибка вероятности около 0.094;
- средний bin-разрыв калибровки около 3.4 процентного пункта.

Нельзя сказать, что «модель права с вероятностью 88.1%»: AUROC — парная ranking-метрика,
а не вероятность правильности одного ответа.

### 7.8. Ranking и калибровка

Это разные свойства:

- **дискриминация/ranking**: правильные ответы получают большие scores; измеряется
  AUROC/AUPRC;
- **калибровка**: среди ответов с вероятностью 0.8 действительно правильны примерно 80%;
  измеряется Brier/ECE.

Преобразование всех scores монотонной функцией не меняет их порядок и AUROC, но может
сильно изменить Brier/ECE. Поэтому слой выбирается по AUROC, а Platt scaling оценивается
отдельно и не участвует в выборе признака.

## 8. Замороженный протокол эксперимента

Чтобы результат одной модели можно было сравнить с другой, нельзя подстраивать метод под
ожидаемый ответ.

Зафиксировано:

- один набор TriviaQA и одно разбиение train/val/test;
- точки A и C;
- один вектор одного слоя;
- стандартизация только по train;
- L2-логистическая регрессия;
- λ из `{100,300,1000,3000}`;
- сначала λ по среднему val AUROC, затем точка/слой по val AUROC;
- test считается один раз;
- `correct_filtered_b` как целевая метка;
- 1000 bootstrap-повторов, seed 42;
- обычно 64 новых токена и `max_len=1024`.

Модельно-специфичные обходы допустимы только когда стандартный шаблон технически не даёт
final-ответ. Они явно описываются и не скрываются:

- gpt-oss — готовый harmony prompt с предзаполненным каналом `final`;
- LFM2.5-2.6B — `<think></think>\nFinal answer:` и `--no-template`;
- LFM2.5-1.2B-Thinking — отдельный reasoning-эксперимент ещё не проведён.

## 10. Что означают результаты

### 10.1. Проба почти всегда лучше baseline

Примеры прироста над лучшим первым токеном:

| модель | лучший baseline | probe | прирост AUROC |
|---|---:|---:|---:|
| Gemma E2B | 0.712 | 0.935 | +0.223 |
| Qwen0.8 Q4 | 0.717 | 0.871 | +0.154 |
| YandexGPT 8B | 0.770 | 0.906 | +0.136 |
| LFM3* | 0.728 | 0.861 | +0.133 |
| LFM2.5-1.2B | 0.765 | 0.881 | +0.116 |
| Qwen4B | 0.878 | 0.918 | +0.040 |
| Qwen9B | 0.877 | 0.917 | +0.040 |

\* Только завершённые строки.

Чем сильнее baseline, тем меньше остаётся дополнительного сигнала для линейной пробы.
Но даже у сильных моделей проба обычно сохраняет положительный прирост.

### 10.2. Средний слой — устойчивый паттерн

| модель | победитель | доля глубины |
|---|---:|---:|
| LFM2.5-1.2B | 9/16 | 56% |
| Qwen3.5-2B | 12/24 | 50% |
| LFM3 | 12/24 | 50% |
| Qwen3.5-4B | 15/32 | 47% |
| Qwen3.5-9B | 16/32 | 50% |
| YandexGPT | 16/32 | 50% |
| Gemma E4B BOS | 20/42 | 48% |
| Gemma E2B | 19/35 | 54% |

Плато соседних слоёв встречается у обычного attention, SWA, рекуррентных/гибридных
архитектур, SSM и MoE. Поэтому оно не выглядит особенностью одного семейства.

### 10.3. Рост правильности и рост AUROC — разные вещи

LFM2.5 показывает это особенно ясно:

- 1.2B: `filtered_b=0.177`, test AUROC 0.8812;
- 2.6B: `filtered_b=0.382`, test AUROC 0.8812;
- парная разница AUROC: +0.0006 [-0.0262,+0.0286].

Модель стала отвечать правильно более чем вдвое чаще, но линейная отделимость правильных
и неправильных ответов не изменилась.

То же видно в Qwen: 4B → 9B подняло правильность 0.454 → 0.570, но AUROC осталось
0.918 → 0.917.

### 10.4. Квантование сдвигает ответы, но не обязательно пробу

Для Qwen0.8 есть BF16 и Q4_K_M:

- ответы текстово совпали примерно на 32% строк;
- `filtered_b` снизилась 0.143 → 0.118;
- победитель остался C/13, λ=1000;
- test AUROC изменилась 0.857 → 0.871;
- парный интервал разницы включает ноль.

Веса пробы между этими двумя квантами переносятся почти без потерь. Это не гарантируется
для других моделей и квантов.

### 10.5. BOS может сильно менять ответы

Повтор Gemma E4B с исправленным BOS:

- `filtered_b`: 0.383 → 0.470;
- ответы совпали на 2907/6000 строках;
- победитель C/21 → C/20;
- test AUROC 0.931 → 0.919;
- парная разница −0.0126 [-0.0259,+0.0012], то есть статистически накрывает ноль.

Получается, prompt сильно изменил фактические ответы, но среднеслойное направление
уверенности сохранилось.

### 10.6. YandexGPT и сильные модели

YandexGPT отвечает правильно почти как Qwen9B: 0.568 против 0.570. При этом её baseline
заметно слабее: entropy AUROC 0.770 против 0.877. Скрытая проба компенсирует большую часть
разрыва и даёт 0.906.

Парно Yandex не отличается от Qwen9B и Gemma E4B BOS; от gpt-oss она погранично ниже на
−0.0195 [-0.0383,−0.0003].

### 10.7. Общий потолок текущего метода

Лучшие значения разных семейств:

- Gemma E2B: 0.935;
- старый Gemma E4B: 0.931;
- gpt-oss-20b: 0.925;
- Gemma E4B BOS: 0.919;
- Qwen4B/9B: 0.918/0.917;
- YandexGPT: 0.906.

Многие парные интервалы внутри этой группы включают ноль. Это поддерживает гипотезу, что
потолок около 0.92–0.94 задаётся однослойным линейным признаком, а не нехваткой параметров
или знаний у модели.

### 10.8. Серия размеров Qwen3.5

Все размеры серии после якоря запускались в Q4_K_M от unsloth.

| размер | слои × D | `filtered_b` | entropy baseline | probe | C-слой |
|---|---:|---:|---:|---:|---:|
| 0.8B | 24×1024 | 0.118 | 0.717 | 0.871 | 13 |
| 2B | 24×2048 | 0.253 | 0.794 | 0.885 | 12 |
| 4B | 32×2560 | 0.454 | 0.878 | 0.918 | 15 |
| 9B | 32×4096 | 0.570 | 0.877 | 0.917 | 16 |

Парный bootstrap:

- 2B − 0.8B: +0.0154 [−0.019,+0.051];
- 4B − 0.8B: +0.0482 [+0.018,+0.080];
- 4B − 2B: +0.0321 [+0.008,+0.054];

### 10.10. gpt-oss-20b

gpt-oss — MoE-модель в MXFP4. Она не помещается целиком в 6 ГБ VRAM и работает с
`-ngl 11`. При `-ngl 12+` часть данных вытеснялась в shared memory, и скорость падала.

Обычный чат-шаблон отправлял генерацию в reasoning-канал. Решение — готовый harmony
prompt, заканчивающийся открытым `final`. После этого:

- 6000/6000 строк, 27 обрезок;
- `filtered_b=0.490`;
- baseline 0.828/0.841;
- probe C/16, test 0.925;
- `--batch-rows 8` ускорил 200 строк примерно в 2.8 раза относительно batch_rows=1.

Точка A у gpt-oss отличается от обычной: это последний токен предзаполненного канала
final. Поэтому результаты A между gpt-oss и другими моделями требуют оговорки. Победила C.

### 10.11. Nemotron 3 Nano 4B

Nemotron сочетает SSM и attention. `l_out` создаётся только на 17 слоях из 42:

```text
1, 3, 5, 8, 10, 13, 15, 18, 20, 22, 25, 27, 29, 33, 37, 39, 41
```

Старый инструмент требовал все 42 и записал нулевые массивы; эти каталоги помечены как
непригодные. Исправленный инструмент автоматически выбрал 17 доступных слоёв.

Валидный результат:

- `filtered_b=0.285`;
- baseline 0.802/0.816;
- probe C/20, test 0.882;
- shuffled 0.481±0.035;
- слой 20 соответствует примерно 49% полной архитектурной глубины.

Кривая разрежена, поэтому ширину плато между отсутствующими слоями оценить нельзя.

### 10.12. LiquidAI

LFM2.5-1.2B Instruct — самый быстрый полный локальный прогон: около 5 минут. Она отвечает
правильно лишь на 17.7% размеченных строк, но probe достигает 0.881.

LFM2.5-2.6B потребовала закрыть reasoning и предзаполнить final. Доля правильных выросла
до 38.2%, AUPRC — с 0.688 до 0.815, но AUROC осталась 0.881. AUPRC выросла в том числе
из-за большего base rate.

LFM3 имеет tri-hybrid архитектуру: 13 gated short convolutions, 5 sliding-window
attention и 6 global attention слоёв. Её официальный режим предполагает sampler и
длинные agentic outputs. В нашем raw greedy/64 режиме 41.8% строк не завершились, поэтому
probe 0.861 относится к выбранному подмножеству и имеет широкий интервал.

Thinking-вариант 1.2B пока не входит в таблицу probe: он выбран для отдельного сравнения
с ограниченным reasoning budget, а не для принудительного no-thinking режима.

### 10.13. Кросс-модельные scores и перенос весов

Есть два разных вопроса:

1. **Можно ли применить веса одной пробы к состояниям другой модели?**
   Обычно нет: размерности различаются, а при одинаковом D пространства всё равно имеют
   разные базисы. Прямой перенос Gemma E4B ↔ Qwen4B дал AUROC 0.325/0.429.

2. **Может ли score одной модели ранжировать метку другой на тех же вопросах?**
   Иногда да, потому что модели разделяют общую сложность вопросов. Например, старые
   кросс-скоры лежали примерно в диапазоне 0.68–0.83.

Высокий чужой score не доказывает перенос «направления уверенности». Если ответы двух
моделей согласованы, бинарная метка одной модели уже предсказывает часть метки другой.
Поэтому в кросс-анализе нужен контроль «знать исход другой модели», а лучше — анализ
внутри страт её правильности.

## 11. Особые режимы и известные аномалии

### 11.1. gpt-oss-20b

Штатные `--no-thinking` и reasoning budget не действуют на наш raw generator. Используется
готовый harmony prompt с уже открытым каналом `final` и `--no-template`.

Точка A здесь — последний токен предзаполненного final-промпта, а не стандартный assistant
marker. `--batch-rows 8` нужен для приемлемой скорости.

### 11.2. Nemotron 3 Nano 4B

Архитектура `nemotron_h` публикует `l_out` только на 17 слоях из 42. Остальные слои не
нулевые и не «потеряны»: публичного `l_out` на них просто нет.

### 11.3. LFM2.5-1.2B-Thinking

Модель намеренно выбрана как reasoning-пара к Instruct. Общий лимит 64 дал 200/200
обрезок. Это не отрицательный итог модели: позже нужен отдельный протокол с ограниченным
reasoning budget, отдельным final budget и явным правилом извлечения final.

До фиксации такого протокола её результаты нельзя смешивать с no-thinking таблицей.

### 11.4. LFM2.5-2.6B

Её шаблон при `thinking=false` всё равно открывает `<think>`. Рабочий вход заканчивается:

```text
<|im_start|>assistant
<think></think>
Final answer:
```

Поэтому A нестандартна: это последний токен `Final answer:`. Победила C, которая имеет
обычное определение.

### 11.5. LFM3-1.7B

2509/6000 ответов не завершились за 64 токена. У завершённых и обрезанных ответов часто
видны самоисправления и лишние `</think>`.

Наиболее вероятна комбинация трёх факторов:

1. официально `enable_thinking=false` может быть нестабилен;
2. GGUF рекомендует `temperature=0.1`, `top_k=50`, `repeat_penalty=1.1`, а наш raw argmax
   sampler не использует;
3. официальный пример допускает 2048 новых токенов, у нас лимит 64.

Это пока гипотеза. Дешёвый будущий контроль — тот же локальный GGUF через `llama-cli` с
официальными sampling parameters, тем же pilot и лимитом 64. Ничего скачивать не нужно.

Источники:

- <https://huggingface.co/LiquidAI/LFM3-1.7B>
- <https://huggingface.co/LiquidAI/LFM3-1.7B-GGUF>
- <https://huggingface.co/LiquidAI/LFM3-1.7B-GGUF/discussions/1>
- <https://huggingface.co/LiquidAI/LFM3-1.7B-GGUF/discussions/6>

Текущая probe 0.861 относится только к 3491 завершённому ответу и может быть смещена
из-за отбора.

### 11.6. Gemma 4 12B

Первый полный прогон был без BOS и непригоден. Валидный v3 имеет 6000/6000 строк,
`filtered_b=0.572` и baseline 0.813/0.826. Его probe отложена по решению пользователя.

Дефектный прогон выглядел технически успешным (`ok=6000`), но 38% строк были обрезаны,
а strict среди завершённых ответов составляла около 0.2%. Модель отвечала мета-текстом
вроде `The answer is the answer`. Это показало, почему gate обязан читать ответы, а не
только проверять форму NPY.

После BOS-fix easy8 дала 7/8, пилот 40 — 0 обрезок и 0 мета-текста, full — 21 обрезку.
Вся Kaggle-сессия заняла 61 минуту, из них основной прогон — 33.5 минуты.

У 12B также есть `tokenizer.ggml.suppress_tokens` для мультимодальных токенов. В новых
версиях llama.cpp их подавляет sampler, но наш raw argmax sampler не вызывает. Поэтому
инструмент исключает эти id вручную.

### 11.7. Версии llama.cpp

Две копии сохранены намеренно:

| каталог | upstream | назначение |
|---|---|---|
| `llama.cpp-hiddenstates` | `d4cff114c`, build 9869 | историческое воспроизведение |
| `llama.cpp-hiddenstates-new` | `785322d17`, build 12033 | новые локальные модели |

На Qwen0.8 Q4 смена версии дала небольшой сдвиг состояний и 75% совпадения ответов, но
метки совпали на 97.3%, победитель остался C/13, а разница AUROC включила ноль. Версии
статистически сопоставимы для этой пробы, но не побитово эквивалентны.

### 11.8. `truncated`, пустой ответ и mismatch — разные состояния

- `truncated=true`: генерация не встретила EOG; текст может быть длинным и даже содержать
  правильный фрагмент, но финальный ответ неизвестен. Метка null.
- пустой завершённый ответ: модель сразу остановилась или текст нормализовался в пустую
  строку. Метка тоже null.
- `retokenize mismatch`: текст есть и может иметь метку, но повторная токенизация дала
  другие id. Строка не удаляется; mismatch служит диагностикой точности точки C.
- `skipped`: состояние не рассчитано, например из-за превышения `max_len`; соответствующая
  строка NPY остаётся нулевой.

Нельзя заменять truncated на 0: это смешало бы «модель явно ответила неправильно» и
«модель не успела сформировать окончательный ответ».

### 11.9. Примеры аномалий ответов

- Gemma E2B: несколько пустых/односимвольных ответов и редкие `<|channel>thought`;
- LFM2.5-2.6B: 10 пустых завершённых ответов;
- LFM3: лишние `</think>`, самоисправления и 2509 обрезок;
- YandexGPT: 20 завершённых ответов содержали кириллицу; отдельная транслитерация не
  добавлялась;
- Gemma 12B v3: два завершённых ответа содержали `<|channel>thought`;
- Qwen2B: один вырожденный ответ `#` сохранён с null-меткой.

Эти строки сохраняются в `meta.jsonl`. Документирование аномалии предпочтительнее ручной
правки ответа после генерации.

### 12.8. Регрессионные проверки инструмента

После изменений C++ повторяются не только model-pilot, но и проверки формата:

| проверка | ожидаемый результат |
|---|---|
| batch vs v1 при `--no-template` | первая строка batch побитово равна массиву v1 |
| два одинаковых запуска | SHA-256 обоих NPY совпадает |
| один prompt с ответом и без | A побитово одинакова |
| пример без ответа | A и C совпадают |
| `--layers step=2` | строки совпадают с теми же слоями полного массива |
| `--layers 4,8,12` | форма `[N,3,D]`, значения совпадают с full |
| слишком длинный пример | `status=skipped`, код процесса 0, NPY-строка нулевая |
| NaN/Inf | отсутствуют |
| resume | уже готовые строки не меняются, пропуски восстанавливаются по `row` |
| неполный `l_out` Nemotron | 17 реальных слоёв, а не 42 нулевых |

Численное совпадение разных версий llama.cpp не ожидается. Для него используется
`compare_runs.py`: median absolute difference, cosine, ответы, позиции, logprob и метки.

### 13.1. Пример строки meta.jsonl

```json
{
  "id": "sfq_21874",
  "row": 0,
  "split": "train",
  "status": "ok",
  "generated": true,
  "truncated": false,
  "n_tokens": 51,
  "pos_a": 48,
  "pos_c": 50,
  "answer": "Hyperlink",
  "logprobs": [-0.02, -0.31],
  "entropies": [0.10, 0.42]

```

`row` — индекс первой оси NPY. Нельзя полагаться на позицию строки в файле при resume;
Python-скрипты читают именно `row`.

### 13.2. Что важно в config.json

| поле | смысл |
|---|---|
| `model` / `model_name` | путь и имя GGUF |
| `n_layers`, `n_embd` | полная глубина и D |
| `layers` | фактически сохранённые id слоёв |
| `layers_requested` | исходный запрос, если часть `l_out` недоступна |
| `max_len`, `max_new_tokens` | лимиты контекста и ответа |
| `template`, `thinking` | применялся ли шаблон и его флаг thinking |
| `batch`, `n_examples` | входной JSONL и ожидаемое число строк |
| `llama_cpp_commit`, `ggml_version` | provenance бинарника |

У архивной копии llama.cpp без `.git` CMake раньше подхватывал commit родительского
репозитория. Для актуального master build commit/build задаются явно. Для старых
`config.json` истинный upstream указан в документации прогона.

### 13.3. Типичные размеры

Размер одного массива без учёта небольшого NPY-заголовка:

```math
\mathrm{bytes} = N \times L \times D \times 2,
```

потому что float16 занимает 2 байта.

Примеры для 6000 строк:

- Qwen0.8 `[6000,24,1024]`: около 281 MiB;
- Gemma E4B `[6000,42,2560]`: около 1.20 GiB;
- Yandex `[6000,32,4096]`: около 1.46 GiB;
- Gemma 12B `[6000,48,3840]`: около 2.06 GiB.

Поэтому states остаются на диске и читаются через memory mapping; в Git хранятся только
метаданные, метрики и веса probe.

## 14. Ограничения

1. **Метки автоматические.** Они могут пропустить правильный синоним или засчитать
   случайное совпадение.

2. **У каждой модели своя метка.** Если модель A отвечает правильно, а B неправильно,
   их AUROC измеряет разные бинарные исходы. Парная разница отражает и свойства probe, и
   разную структуру ошибок.

3. **AUPRC зависит от доли положительных.** Высокая AUPRC gpt-oss/Yandex частично
   объясняется большим base rate.

4. **Baseline смотрит только первый токен.** Для модели со служебным первым токеном он
   может быть плохо откалиброван.

5. **Проба линейная и однослойная.** Она не использует несколько слоёв, несколько
   позиций, attention/SSM-статистики или нелинейные признаки.

6. **Test используется один раз.** Другие слои на test не сравниваются; это защита от
   подгонки.

7. **Обрезки создают выборочный сдвиг.** Особенно у LFM3, где осталось только 3491/6000
   завершённых ответов.

8. **Генератор — raw greedy.** Он не повторяет sampler LM Studio/llama-cli. Это особенно
   важно для LFM3 и reasoning-моделей.

9. **Старые BOS-дефектные прогоны сохранены.** Gemma E2B/E4B и Nemotron без BOS не
   пересчитывались и должны сравниваться с этой оговоркой.

10. **Версии llama.cpp не побитово равны.** На Qwen разница мала для probe, но меняет
    часть жадных ответов.

11. **Одинаковая размерность не означает одинаковое пространство.** Веса разных семейств
    без выравнивания переносить нельзя.

12. **Gemma 12B пока без probe.** Генерация, метки и baseline готовы; CPU-проба отложена.

13. **Текущий набор — только TriviaQA.** Перенос на другие домены ещё не проверен.

## 16. Краткий словарь

| термин | простое объяснение |
|---|---|
| **GGUF** | файл с весами, токенизатором и метаданными модели для llama.cpp |
| **llama.cpp** | движок локального запуска GGUF-моделей |
| **токен** | элемент последовательности модели; часть слова или специальный маркер |
| **BOS / EOG** | начало последовательности / конец генерации |
| **чат-шаблон** | правило, которое превращает роли user/assistant в служебный текст |
| **логит** | ненормированная оценка следующего токена до softmax |
| **logprob** | логарифм вероятности выбранного токена |
| **энтропия** | неопределённость всего распределения токенов |
| **скрытое состояние** | внутренний вектор слоя для конкретной позиции |
| **слой** | последовательный вычислительный блок модели |
| **тензор** | многомерный массив чисел |
| **`l_out-N`** | тензор выхода слоя N, который читает инструмент |
| **callback / `cb_eval`** | функция, которую llama.cpp вызывает при построении/вычислении графа |
| **A / C** | последний токен prompt / последний содержательный токен ответа |
| **D** | размер скрытого вектора |
| **train / val / test** | обучение / выбор параметров / финальная проверка |
| **label / метка** | 1 для правильного ответа, 0 для неправильного |
| **base rate** | доля единиц в выборке |
| **baseline** | простой ориентир: здесь первый токен ответа |
| **probe / проба** | простой классификатор поверх замороженных состояний |
| **L2-регуляризация** | штраф за большие квадраты весов, уменьшающий переобучение |
| **IRLS** | итеративный алгоритм обучения логистической регрессии |
| **λ** | сила L2-регуляризации; больше — сильнее штраф весов |
| **score** | число до sigmoid, используемое для ранжирования |
| **калибровка** | превращение score в вероятность, согласованную с частотой ошибок |
| **Platt scaling** | логистическая калибровка одного score |
| **precision** | доля правильных среди ответов, поставленных выше порога |
| **recall** | доля всех правильных ответов, найденных выше порога |
| **AUROC** | качество ранжирования единиц выше нулей |
| **AUPRC** | площадь precision–recall; зависит от base rate |
| **Brier** | средняя квадратичная ошибка вероятности |
| **ECE** | средний разрыв между вероятностью и фактической частотой |
| **bootstrap CI** | интервал из повторных выборок строк с возвращением |
| **seed** | фиксированное число, делающее случайные операции воспроизводимыми |
| **`truncated`** | модель не выдала EOG в пределах бюджета токенов |
| **retokenize mismatch** | текст ответа после повторной токенизации дал не те же id |
| **batch / ubatch** | логическая партия / часть партии одного decode |
| **mmap** | чтение нужных участков файла без загрузки всего массива в RAM |
| **квантование** | хранение весов с меньшей точностью для экономии памяти |
| **BF16** | 16-битный формат весов с широким диапазоном |
| **Q4_0 / Q4_K_M** | разные 4-битные схемы квантования GGUF |
| **MXFP4** | 4-битный floating-point формат весов gpt-oss |
| **QAD** | Quantization-Aware Distillation: обучение с учётом будущего кванта |
| **attention / SWA** | полное / оконное внимание к предыдущим токенам |
| **SSM** | state-space блок, альтернатива attention для обработки последовательности |

| **temperature** | насколько сглаживаются логиты перед sampling |
| **top-k** | разрешить sampling только среди k лучших токенов |
| **repeat penalty** | штраф уже встречавшимся токенам для уменьшения повторов |
