# LFM3-1.7B QAD: высокая доля обрезок

Стандартный прогон на llama.cpp `785322d17`, чат-шаблон модели, `thinking=false`,
`--max-new-tokens 64`:

- 6000/6000 `ok`, но **2509/6000 = 41.8% `truncated`**;
- 2090.3 s, 2.87 ex/s;
- `[6000, 24, 2048]`, все 24 `l_out` доступны;
- `filtered_b` 1064/3491 = 0.305;
- baseline test AUROC: logprob 0.728, entropy 0.725.

Штатный шаблон уже заканчивается `<think></think>`. Дополнительный final-cue с явным
`<|startoftext|>` не помог: в тесте 20 строк обрезки выросли с 9 до 12, поэтому полный
прогон оставлен на стандартном шаблоне. В 1025 ответах встречается лишний `</think>`;
разметка не переписывалась. Почему модель игнорирует просьбу о коротком ответе и часто
уходит в самоисправления, экспериментально не доказано. Это не следует автоматически
связывать с намеренным reasoning-режимом LFM2.5-Thinking.

Проба и доля правильных относятся только к 3491 завершённому ответу. Из-за исключения
41.8% строк, не завершившихся в пределах 64 токенов, результат нельзя напрямую
интерпретировать как метрику на всём исходном наборе без этой оговорки.

Проба: λ=1000, **C / слой 12** (12/24), val AUROC 0.8667, test AUROC **0.8608**
[0.832, 0.889], test AUPRC 0.7560. Контроли: shuffled 0.461 ± 0.031, слой 0 C —
0.641 на test. Прирост над лучшим baseline (logprob 0.728): +0.133 AUROC.

На общей тестовой подвыборке от LFM2.5-1.2B (Δ=-0.0135
[-0.0512, +0.0225]), LFM2.5-2.6B (Δ=-0.0218 [-0.0580, +0.0123]) и Qwen3.5-2B
(Δ=-0.0090 [-0.0421, +0.0235]) статистически не отличается. Интервалы широкие из-за
малого числа завершённых тестовых строк (около 700).

## Наиболее вероятная причина обрезок (web-проверка 2026-11-02)

Официальная карточка LFM3 указывает:

- reasoning включён по умолчанию; `enable_thinking=false` может работать нестабильно,
  особенно на reasoning-heavy запросах;
- рекомендуются `temperature=0.1`, `top_k=50`, `repeat_penalty=1.1`;
- обычный пример даёт до 2048 новых токенов, а agentic evaluations используют ещё
  большие лимиты.

Эти sampling-параметры записаны и в официальном GGUF. Наш инструмент их не применяет:
генерация идёт через raw greedy `hs_argmax`, без `common_sampler` и repeat penalty.
Комбинация отсутствующего штрафа повторов, известной нестабильности no-thinking и лимита
64 хорошо объясняет циклы/самоисправления и лишние `</think>`. Это сильная гипотеза, но
не доказательство: локальный контроль с обычным `llama-cli` пока не запускался.

Устаревший движок маловероятен: официальный GGUF требует llama.cpp b11960+, у нас build
12033; prompt совпадает с официальным шаблоном. QAD-Q4_0 — официальный
Quantization-Aware Distillation checkpoint; доказательств, что аномалия вызвана именно
квантом, нет.

Будущая дешёвая проверка на имеющемся файле: тот же pilot и лимит 64 через `llama-cli`
с `temp=0.1`, `top-k=50`, `repeat-penalty=1.1`, `enable_thinking=false`, затем сравнить
долю EOG с raw argmax. Передача этих флагов текущему `llama-hidden-states` ничего не
изменит, потому что его генератор sampler не вызывает.
