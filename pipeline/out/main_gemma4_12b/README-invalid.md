# Этот каталог непригоден для анализа

Полный прогон Gemma 4 12B (6000 строк) снят на Kaggle-ядре `odinodinodin/hs-gemma4-12b`
(2026-11-01, пин `d4cff114c`), технически прошёл целиком, но **модель отвечала
мета-текстом**, а не по существу вопроса, поэтому размеченных строк почти нет.

## Что с прогоном (факты)

- 6000/6000 `ok`, 0 `skipped`; `truncated` **2298 (38.3 %)**, `retokenize mismatch` 12;
  время 8736.8 s (0.69 ex/s на 2 × T4), массивы `[6000, 48, 3840]` f16.
- `verify_run.py --full --input data\main.jsonl` → 0 failed.
- `labels.csv`: `correct_strict` / `correct_relaxed` = **9 / 3702 = 0.002**; null-меток
  2298 (все `truncated`, не отказы).

## Почему непригоден: модель не отвечает на вопрос

Среди «чистых» (не обрезанных) строк доминируют ответы-заглушки, повторяющие
формулировку инструкции:

| ответ | строк |
|---|---|
| `The answer is the answer.` | 880 |
| `The correct answer is **C**.` | 598 |
| `The correct answer is the first option.` | 312 |
| `The correct answer is **A**.` | 147 |
| `The answer is the answer, no explanation.` | 86 |
| `The correct answer is the one that states the correct answer.` | 67 |

Обрезанные строки — те же шаблоны, ушедшие в цикл (`The correct answer is **C**.` ×N,
229+160 строк), либо утечка служебных маркеров в текст
(`<|channel>thought <channel|><|channel>th…` — 316 строк, `<|channel> <|channel> …` — 56),
либо схлопывание слова (`I've've've've…`). Средняя длина ответа у обрезанных — 276.6
символа против 41.9 у чистых; среднее число токенов 104.5 против 49.8.

Доля деградаций по сплитам одинаковая (train 0.382 / val 0.387 / test 0.382), то есть
это не отдельный «трудный» кусок данных, а свойство всего прогона.

## Чем это не объясняется (проверено)

- **Не версия llama.cpp**: на master без правок — те же 0/8 и тот же мета-текст, что на
  пине `d4cff114c` (ядра `hs-gemma4-12b-debug`, `hs-gemma4-12b-pin-gpu`,
  `hs-gemma4-12b-master-gate` v1). `llama-completion` на том же master и той же модели
  отвечает 8/8 — значит дело в нашем инструменте, а не в сборке.
- **Не промпт и не шаблон**: шаблон из GGUF совпадает с официальным
  `google/gemma-4-12B-it/chat_template.jinja` (различия только в обработке tool-call),
  инструмент рендерит канонический Gemma 4-промпт, `template: true` в `config.json`.
- **Не VRAM и не квант как таковой**: та же схема на E4B (Q4_K_M, локально) и на 26B-A4B
  даёт нормальные ответы; пилот 40 строк на 12B воспроизвёл ту же деградацию.
- **Не «слабое семейство»**: E4B на тех же входах размечен нормально (0.383 по
  `filtered_b`), см. `pipeline/out/main_gemma4e4b`.

## Настоящая причина (2026-11-02): потерянный ведущий `<bos>`

Шаблон Gemma печатает в начале `{{ bos_token }}`, а llama.cpp **вырезает** этот `<bos>` из
отрендеренного промпта (`inputs.add_bos = llama_vocab_get_add_bos()`, у 12B `add_bos_token =
true`) и ожидает, что токенизатор добавит токен обратно — так делает `llama-cli`
(`common_tokenize(..., true, true)`). Наш пакетный режим токенизировал шаблонный промпт
с `false`, поэтому BOS терялся.

Проверено на самом GGUF, без загрузки весов (`hs-prompt-dump`, `vocab_only`):

| | токенов | первый токен |
|---|---|---|
| `add_special=false` (как было) | 27 | `105` = `<\|turn>` |
| `add_special=true` (как `llama-cli`) | **28** | **`2` = `<bos>`** |

Второй, мелкий дефект: `tokenizer.ggml.suppress_tokens` у 12B — `<image\|>`, `<audio\|>`;
после коммита `afeebe103` (2026-07-29) llama.cpp применяет их в цепочке сэмплера, а наш
greedy-argmax их не пропускал. Теперь пропускает (`hs_argmax`).

После правок тот же master даёт easy8 **8/8**, мета-текста в пилоте 200 — **0**, скорость
**2.61 ex/s** (было 0.50). Доказательство — `kaggle/gemma4_12b_hs_master/`,
`AGENTS.md` («Потерянный `<bos>`»). Новый прогон нужен в отдельном каталоге
(`out\main_gemma4_12b_v3`), этот каталог остаётся свидетельством.
